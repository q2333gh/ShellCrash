# Web Control Plane 语言选型权衡（针对 `2026-02-13-web-control-plane-api-refactor.md`）

## 1. 选型目标

面向 ShellCrash 的“纯 HTTP API + Web 控制面板”重构，语言选择必须满足：

- 路由器资源受限（内存/CPU/存储）可运行。
- 与现有 `scripts/start.sh`、`scripts/starts/*`、`scripts/libs/*` 低耦合接入。
- 可维护性、安全性、可测试性优于当前 CLI 交互方式。
- 适配 OpenWrt/BusyBox/容器等多环境。

## 2. 候选语言/方案对比

## 方案 A：继续以 Shell 为 API 主实现（CGI/FastCGI）

优点：
- 与现有代码同语言，迁移阻力最小。
- 无额外运行时依赖，部署最简单。
- 可快速验证“Web-First”流程是否可行。

缺点：
- JSON 序列化、路由、中间件、安全机制实现成本高且易出错。
- 长期维护复杂度上升，测试与重构困难。
- 性能与健壮性上限有限（并发、异常处理、输入安全）。

结论：适合短期过渡，不适合长期控制平面核心。

## 方案 B：Lua（配合 uhttpd / LuCI 生态）

优点：
- OpenWrt 生态兼容性高，体积小。
- 比 Shell 更适合写 HTTP 路由与 JSON API。
- 运维侧对路由器 Lua 方案接受度较高。

缺点：
- 与现有 Shell 业务仍有“跨语言边界”问题。
- 团队如果缺少 Lua 经验，维护门槛会上升。
- 跨非 OpenWrt 环境时一致性不如 Go。

结论：对 OpenWrt 很友好，但跨平台统一性一般。

## 方案 C：Go（独立 control-plane daemon）

优点：
- 静态编译单二进制，部署简单，跨平台能力强。
- 原生 HTTP/JSON/并发模型成熟，安全与可测试性明显更好。
- 便于建立清晰分层：API 层、服务层、Shell 执行适配层。
- 与现有内核生态（mihomo/sing-box 同为 Go 生态）一致，工程协作更顺畅。

缺点：
- 首期需要建立新工程骨架与打包流程。
- 比纯 Shell 方案引入更高的初始改造成本。

结论：长期最优解，适合作为主选语言。

## 方案 D：Rust（独立 daemon）

优点：
- 性能与内存效率优秀，类型安全强。
- 适合高可靠控制平面实现。

缺点：
- 团队学习与开发成本高于 Go。
- 与现有工程栈不一致，首期推进风险大。

结论：技术上可行，但当前阶段性价比不高。

## 方案 E：Node.js/Python

优点：
- Web 开发效率高（开发期）。

缺点：
- 运行时依赖重，路由器部署与运维成本明显上升。
- 与资源受限场景不匹配。

结论：不建议作为路由器端控制平面主方案。

## 3. 推荐选择

推荐：**C（Go）为主 + A（Shell）为过渡**。

原因：
- 你的重构计划要求“快速替换入口交互层”与“长期可维护 API 控制面”同时达成。
- 纯 Shell 可以最短时间打通功能，但长期风险高。
- Go 在路由器场景下可保持较小体积和较强工程性，最平衡。

## 4. 分阶段落地策略（与现有计划对齐）

阶段 1（快速落地，2-4 周）：
- 使用 Shell 实现最小 API（健康检查、状态、启停、初始化向导）。
- Web 面板先跑通关键用户流程。
- 保留 CLI 兼容层。

阶段 2（稳态演进，4-8 周）：
- 引入 Go control-plane daemon，复刻阶段 1 API 契约。
- Shell API 层降级为兼容适配或逐步下线。
- 把认证、CSRF、限流、审计日志等安全能力固化在 Go 层。

阶段 3（收敛，1-2 个版本周期）：
- 将菜单交互彻底转为“只读提示 + 运维命令”。
- API 成为唯一交互入口；文档与 CI 全面围绕 API/Web。

## 5. 关键技术边界建议

无论采用 Shell 或 Go，需固定以下边界：

- `scripts/start.sh` 与 `scripts/starts/*` 视为“执行引擎”，不直接暴露给前端。
- 所有外部输入只经 API 参数校验层进入执行层。
- API 错误码与响应结构先定协议，再实现语言迁移。
- 禁止前端直接拼接命令；必须通过白名单动作调用。

## 6. 最终决策建议（可直接用于评审）

- **主语言决策：Go（长期）**
- **过渡语言决策：Shell（短期）**
- **不采纳：Node/Python 作为路由器端主实现**
- **有条件备选：Lua（如果明确仅服务 OpenWrt 发行形态）**

该决策能在不阻断当前重构节奏的前提下，兼顾上线速度与长期工程质量。
