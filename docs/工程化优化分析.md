# ShellCrash 工程化优化分析（仓库现状）

## 1. 当前工程化现状概览

基于当前仓库（`X:\code\ShellCrash`）扫描结果：

- 代码主体为 Shell 脚本：约 83 个 `.sh` 文件（`scripts/` 为主）。
- GitHub Actions 工作流较多：9 个工作流（` .github/workflows/`）。
- 自动化流程覆盖了构建、打包、发布、资源更新，但缺少质量门禁型 CI。
- 仓库直接存放大量二进制产物（`bin/` 下多架构压缩包，单文件 9-11MB 常见）。
- 缺少常见工程规范基线文件（未发现 `.editorconfig`、`.gitattributes`、`.shellcheckrc`、`Makefile`、`Taskfile.yml`）。

这说明项目在“发布自动化”方面投入较多，但在“质量稳定性、可维护性、安全性”方面还有系统优化空间。

## 2. 关键优化点（按优先级）

## P0（高优先级，建议先做）

### 2.1 增加基础 CI 质量门禁（ShellCheck + 基础冒烟测试）

现状证据：

- ` .github/workflows/test.yaml` 实际在做 core 构建，不是对本仓库脚本的质量验证。
- 目前缺少对 `scripts/**/*.sh` 的静态检查与最小执行验证。

风险：

- Shell 脚本语法、引用、未定义变量、兼容性问题不能在 PR 阶段提前发现。
- 回归问题更容易在用户环境暴露。

建议：

- 新增 `ci-shell.yml`：
  - `shellcheck` 检查 `install.sh`、`install_en.sh`、`scripts/**/*.sh`、`tools/**/*.sh`。
  - 至少增加 1 组容器冒烟测试（例如 `sh -n` + 关键入口脚本最小执行路径）。
- 将该工作流设为必过检查（分支保护策略）。

### 2.2 统一与加固 GitHub Actions 安全策略

现状证据：

- 多个工作流使用 `permissions: write-all`（如 `core_auto_update.yml`、`core_easy_update.yaml`）。
- 存在 `@main` 或浮动版本引用（如 `release_new_version.yaml` 的 `actions/checkout@main`、`actions/upload-artifact@main`）。
- 第三方 Action 未全面 pin 到 commit SHA（如 `softprops/action-gh-release@v1`、`Mattraks/delete-workflow-runs@main`）。

风险：

- 供应链风险与权限过大风险叠加。
- 上游 Action 变更可能导致不可预期故障。

建议：

- 对每个工作流最小化 `permissions`（按 job 粒度分配 `contents: read/write` 等）。
- 全部 action 固定到 commit SHA（至少关键发布链路优先处理）。
- 对发布类 workflow 增加 `concurrency`，避免重复触发并发写分支。

### 2.3 避免在自动化中重写分支历史

现状证据：

- `bin_update.yml` 中存在 `rm -rf .git` + `git init` + `git push -f origin update`。

风险：

- 历史不可追溯，审计困难。
- 并发或失败回滚时故障定位成本高。

建议：

- 改为常规增量提交；确需强制推送时至少保留审计日志与变更摘要。
- 把“资源发布分支”与“源码分支”职责进一步隔离（例如通过 Release Asset / OCI Artifact）。

## P1（中优先级，建议随后推进）

### 2.4 降低工作流重复与维护成本（抽象共用逻辑）

现状证据：

- `test.yaml`、`update_meta_core.yaml`、`update_singbox_core.yaml` 存在较多重复步骤（获取 Go 版本、矩阵打包、上传制品、发布）。

建议：

- 抽象为复用 workflow 或脚本模板，统一参数输入。
- 将“构建”“打包”“发布”“清理”解耦，减少单文件工作流复杂度。

### 2.5 引入可复现构建策略

现状证据：

- 工作流动态抓取 latest Go 版本。
- 构建和资源下载普遍缺少 checksum 验证。

风险：

- 同一 tag 在不同时间构建出不同结果，不利于问题复盘。

建议：

- 固定 Go 主/次版本（例如 `1.2x.y`，按周期人工升级）。
- 对 UPX、核心二进制、规则数据等下载资源增加校验（SHA256）。

### 2.6 安装脚本去重与国际化策略优化

现状证据：

- `install.sh` 与 `install_en.sh` 均为 363 行，结构高度相似。

风险：

- 两份逻辑长期演进易偏离，修复需双改。

建议：

- 抽出共用安装逻辑，语言文本外置（复用 `scripts/lang` 思路）。
- 保留双入口，但将差异收敛为语言资源层。

## P2（低优先级，持续改进）

### 2.7 建立基础工程约定文件

建议补齐：

- `.editorconfig`：统一缩进、行尾、编码。
- `.gitattributes`：脚本行尾策略（LF）与二进制识别。
- `.shellcheckrc`：明确忽略规则与目标 shell 方言。

### 2.8 文档体系化

建议新增：

- `docs/engineering/`：工程规范与发布流程文档。
- `CONTRIBUTING.md`：本地验证命令、提交流程、PR 要求。
- PR 模板：要求附验证结果和风险说明。

## 3. 推荐落地路线图（可执行）

### 阶段 1（1-3 天）

- 新增 CI 质量门禁工作流（ShellCheck + `sh -n` 冒烟）。
- 将发布关键工作流的 Action 固定版本（先从 `@main` 改掉）。
- 为关键 workflow 增加最小权限与并发控制。

### 阶段 2（3-7 天）

- 抽象重复 workflow 逻辑，统一构建参数。
- 下载资源增加 SHA256 校验。
- 补齐 `.editorconfig` / `.gitattributes` / `.shellcheckrc`。

### 阶段 3（1-2 周）

- 安装脚本共用逻辑重构（中英文入口仅保留文案差异）。
- 重构 update 分支产物策略，减少强制改写历史。
- 完成贡献文档与发布流程文档沉淀。

## 4. 建议优先追踪的度量指标

- CI 首次失败拦截率（上线后 4 周）。
- 发布失败率与回滚次数。
- 工作流平均执行时长与重试率。
- 安装脚本相关 issue 占比变化。

---

如果要进入实施阶段，建议先从“P0.1 + P0.2”开始，它们对稳定性和安全性的收益最高，且改造风险最低。
