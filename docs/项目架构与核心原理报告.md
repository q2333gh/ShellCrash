# ShellCrash 项目架构与核心原理报告

## 1. 项目定位

ShellCrash 是一个基于 Shell 的代理管理与流量转发编排系统，核心目标是：

- 在异构 Linux/路由器/容器环境中统一部署与管理代理内核。
- 在运行时按设备能力动态选择启动方式与防火墙实现（`iptables`/`nftables`）。
- 将“订阅配置获取 -> 配置校验与改写 -> 内核启动 -> 流量接管 -> 运维任务”串成一条自动化链路。

核心内核支持以 `crashcore` 为抽象变量统一管理，主要包含 `meta(mihomo)`、`singbox`、`singboxr`。

## 2. 总体架构

从职责上可分为 5 层：

1. 入口与交互层
- 入口脚本：`scripts/menu.sh`（交互菜单/CLI 参数）、`scripts/start.sh`（服务启停）。
- 菜单逻辑：`scripts/menus/*.sh`，按功能模块拆分（设置、任务、网关、升级、工具等）。

2. 配置与状态层
- 主配置：`scripts/configs/ShellCrash.cfg`（运行参数）。
- 运行命令：`scripts/configs/command.env`（内核启动命令、目录变量）。
- 配置读写：`scripts/libs/get_config.sh`、`scripts/libs/set_config.sh`。

3. 内核与配置编排层
- 核心管理：`scripts/libs/core_tools.sh`（下载、解包、校验、切换）。
- 配置获取：`scripts/starts/core_config.sh`（订阅转换与远程配置拉取）。
- 配置验真：`scripts/starts/clash_config_check.sh`、`scripts/starts/singbox_config_check.sh`。
- 启动前检查：`scripts/starts/clash_check.sh`、`scripts/starts/singbox_check.sh`。

4. 流量接管与系统集成层
- 防火墙总控：`scripts/starts/fw_start.sh`、`scripts/starts/fw_stop.sh`。
- 后端实现：`scripts/starts/fw_iptables.sh`、`scripts/starts/fw_nftables.sh`。
- 多 init 体系适配：procd/systemd/openrc/s6/保守模式（由 `scripts/start.sh` 分派）。

5. 交付与运维自动化层
- GitHub Actions：`.github/workflows/*.y*ml`。
- Docker 交付：`Dockerfile` + `docker/s6-rc.d/*`。
- 二进制与规则资源：`bin/`。

## 3. 目录与职责映射

- `scripts/libs/`：通用库函数，原则上不直接输出 UI 文案。
- `scripts/menus/`：交互菜单与用户操作编排。
- `scripts/starts/`：启动链路、网络接管、配置生成与校验。
- `scripts/lang/`：中英文文本资源（i18n）。
- `tools/`：附加工具脚本。
- `docker/`：容器运行编排与 s6 服务定义。
- `.github/workflows/`：构建、打包、发布、资源更新自动化。

该划分体现了“交互逻辑”和“系统执行逻辑”分离，便于在非交互场景（开机自启、容器）复用同一启动内核。

## 4. 核心功能

1. 多内核管理与自动匹配
- 通过 `crashcore` 统一抽象，按配置能力自动切换核心（例如检测到某些特性时升级到 `meta` 或 `singboxr`）。
- 相关实现：`scripts/starts/core_exchange.sh`、`scripts/starts/clash_check.sh`、`scripts/starts/singbox_check.sh`。

2. 订阅/配置在线获取与转换
- 支持从远程服务拉取配置，并按目标内核格式生成 YAML/JSON。
- 拉取失败时支持服务器轮转与重试。
- 相关实现：`scripts/starts/core_config.sh`。

3. 配置校验与自动修正
- 启动前验证配置是否包含有效节点、是否为兼容版本、是否存在不支持字段。
- 在必要时移除无效策略组并清理格式问题。
- 相关实现：`scripts/starts/clash_config_check.sh`、`scripts/starts/singbox_config_check.sh`。

4. 多模式流量转发
- 支持本机代理、旁路由、主旁路转发、`Tun/Redir/Tproxy/Mix` 等模式。
- 使用策略路由（`fwmark` + `table`）与防火墙规则接管流量。
- 相关实现：`scripts/starts/fw_start.sh`、`scripts/starts/fw_stop.sh`。

5. 跨系统服务化启动
- 兼容 procd（OpenWrt）、systemd、openrc、s6（Docker）及保守模式。
- 相关实现：`scripts/start.sh`。

6. 任务与自维护能力
- 启停后钩子任务、cron 任务、配置持久化恢复、日志调试。
- 相关实现：`scripts/starts/bfstart.sh`、`scripts/starts/afstart.sh`、`scripts/start.sh`。

## 5. 关键工作原理

## 5.1 初始化原理（一次性/重建）

初始化由 `scripts/init.sh` 执行，核心流程是：

- 识别运行环境（路由固件、容器、标准 Linux）。
- 选择安装目录与服务接入方式（写入 procd/systemd/openrc/s6 对应入口）。
- 生成/修正 `ShellCrash.cfg` 与 `command.env`。
- 设置 `COMMAND` 变量，统一内核启动命令格式：
  - mihomo：`CrashCore -d ... -f config.yaml`
  - sing-box：`CrashCore run -D ... -C jsons`

这一步把“系统差异”收敛掉，后续运行链路只依赖统一变量。

## 5.2 启动编排原理（前置 -> 启动 -> 后置）

启动由 `scripts/start.sh start` 编排，分三段：

1. 前置阶段（`bfstart.sh`）
- 加载配置默认值。
- 检查网络、核心文件、地理数据库、配置文件可用性。
- 根据 `crashcore` 对配置进行校验与改写，准备运行时文件到 `TMPDIR`。

2. 内核启动阶段
- 按 init 体系选择启动路径：procd/systemd/openrc/s6/保守模式。
- 实际执行命令统一来自 `command.env` 的 `COMMAND`。

3. 后置阶段（`afstart.sh`）
- 检测进程是否成功运行。
- 注入防火墙/策略路由规则。
- 恢复面板配置、装载 cron 与自定义任务。

该三段式设计把启动成功率和可观测性分层处理，便于定位故障点。

## 5.3 配置处理原理（拉取、验真、落盘）

- 拉取：`core_config.sh` 根据订阅链接和模板服务生成目标配置。
- 验真：按核心类型调用对应 `check_config`，拦截无节点、旧格式、不兼容字段。
- 落盘：新配置与旧配置比对，不同才替换，并保留备份。

这套流程保证“配置可用性优先”，避免错误配置直接导致服务不可用。

## 5.4 核心切换原理（能力驱动）

- 启动前扫描配置特征与运行模式。
- 当当前核心不满足能力时，通过 `core_exchange` 触发核心切换。
- `core_tools.sh` 负责二进制解包、签名式行为校验（通过帮助输出与版本命令判断兼容）并写回状态。

本质上是一个“按能力自动升级内核”的策略，减少用户手动决策负担。

## 5.5 流量接管原理（规则 + 路由）

- `fw_start.sh` 根据 `firewall_area`、`redir_mod`、`dns_mod` 组合策略。
- 通过 `ip rule` + `ip route table` + `fwmark` 完成策略路由。
- 通过 `iptables` 或 `nftables` 注入 DNS 劫持、TCP/UDP 转发、例外放行与 QUIC 处理规则。
- `fw_stop.sh` 完整回滚链路，清理自建链、路由策略、临时修复项。

该机制使 ShellCrash 既能作为本机代理，也能作为网关/旁路设备工作。

## 5.6 容器运行原理

Docker 场景使用 s6 作为进程编排：

- `docker/s6-rc.d/bfstart/up`：调用 `/etc/ShellCrash/start.sh bfstart`
- `docker/s6-rc.d/shellcrash/run`：执行 `COMMAND` 启动核心
- `docker/s6-rc.d/afstart/up`：调用 `/etc/ShellCrash/start.sh afstart`
- `docker/s6-rc.d/crond/run`：前台运行 cron

容器模式沿用同一启动三段式，仅替换为 s6 服务编排。

## 6. 架构特点总结

- 高兼容：通过 init 体系与防火墙后端双适配覆盖多类系统。
- 强编排：配置、核心、网络、任务形成闭环启动链。
- 可演进：目录分层明确，功能可按库/菜单/启动链独立迭代。
- 可运维：内置调试、定时任务、自动恢复与资源更新机制。

同时，其复杂度主要集中在 Shell 运行时分支和平台差异处理上，后续演进建议继续加强自动化测试与配置契约校验。
